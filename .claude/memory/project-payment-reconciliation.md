Explained to user 2026-08-23 (report-only, no code changes). Payment fulfillment = Razorpay webhook (`payment.captured`) → `process_payment` RPC (supabase/schema.sql) doing ONE atomic pair of writes: `premium_purchases` ledger row (payment_id is the unique idempotency anchor; amount in rupees) + `profiles.premium_plan`/`premium_expires_at` (+7/30/90/365 days). **Premium = `premium_expires_at > now()`** — there is no boolean flag. `/api/verify-payment` only READS so the UI unlocks early; webhook is source of truth.

Failure mode: webhook 5xx-retries on missing userId/plan notes, unknown plan, non-INR, or amount ≠ order-time pin → after retries exhausted it appears in **Razorpay Dashboard → Settings → Webhooks → failed deliveries**; reason in Vercel logs (grep `[webhook]`). Money stays captured.

Manual check: confirm `captured` + Notes(userId/plan) in Razorpay Payments, then SQL `premium_purchases` by payment_id/user email. Row exists = fulfilled (check expiry or refunded_at instead); captured-but-no-row = failed fulfillment → grant manually; no capture in Razorpay = user never paid.

**Manual grant = replay the RPC in Supabase SQL editor** with real values from the dashboard incl. `p_expected_paise` (validates against what was actually paid, immune to site_settings price drift). Idempotent on payment_id. NEVER bare-`update profiles` — that skips the purchase row and breaks refund attribution + referral commissions.
